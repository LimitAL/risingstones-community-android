# 官方移动站原生移植记录

## 2026-09-20 论坛与招募首次互动设计

1. 范围仅为已核对的官方论坛点赞、收藏、评论、删除、投票、评论图片上传，以及副本/新人
   招募回应和跑团评论点赞；复用现有功能模块，不新增模块组。请求路径、表单与结果各自保持
   官方契约，不以一种动作的字段猜测其他动作。
2. 增加可选的操作资格扩展，与已经验证的写能力分开。账号读取成功只提供尝试资格；旧服务
   的写能力属性仍表示真实能力。参考界面的点赞/收藏按钮、最终发送与投票按钮是明确操作，
   删除继续使用确认弹窗。选图只读取本地内容，最终发送才上传，后台加载不触发写请求。
3. 论坛使用 `ForumWrite`，上传独立使用 `ForumImageUpload`，招募使用 `RecruitmentWrite`。
   每次写入绑定当前凭证，响应结构通过校验后才完成能力授予；身份冲突和认证失败不自动重放。
   图片先取得官方 COS 临时令牌，在 PUT 前再次校验同一次尝试仍属于当前凭证，上传成功才授予。
4. 招募回应仍要求明确不是作者本人。首次尝试使用已有 `AccountRead` 读取绑定角色后比较，
   身份未知或本人不允许回应；该只读比较不授予任何写能力。部队读取继续独立受其读取能力约束。
5. domain 提供可选资格接口；data 管理凭证绑定、响应校验和单次请求；presentation 区分
   可尝试与已验证，沿用忙碌、草稿与失败保留；UI 接入明确动作并随资格撤销清理。app 继续
   使用凭证版本释放旧模型，不把登录成功当作全部能力成功。
6. 沿用紧凑单栏、中等与展开列表/详情布局，保持现有选择与草稿。测试覆盖首次动作、无资格、
   负载缺失、失败不重试、换号/退出/取消、上传两阶段、回应作者限制和四个宽度；更新公共
   Maven 消费、三语资源、安全门禁及兼容性记录。真实写入仍须用户选择具体操作后验证。

实际窗口截图补充发现：600dp 双栏详情中，评论头部的操作按钮会挤压作者名。评论作者信息
与操作改为独立两行，按钮可自然换行，并在四档设备用例中读取实际文字排版结果，确认合成
作者名没有溢出或逐字堆叠；这项修复不改变顶层导航和阅读栈。

## 2026-09-20 首次明确操作与招募读取验证设计

1. 范围仅为官方部队招募读取、签到及领奖。部队验证复用官方 GET
   `api/home/recruit/recruitGuildList?page=1&limit=1`，接受响应且 `data.rows` 为数组才授予
   `RecruitmentAuthenticated`；失败移除该读取能力并保留其他已验证能力，绝不授予招募写能力。
2. 首次签到和领奖仍分别使用官方 POST `sign/signIn` 与 `sign/getSignReward`。
   界面明确确认本次实际操作后才调用；不是后台探测。匿名状态不开放，已验证账号读取能力只
   允许开始尝试，不表示签到成功。成功响应的有效领域负载才作为本次写能力证据。
3. 在 `core` 增加可选的单次能力尝试契约，授权器限定请求上下文；`auth-webview` 绑定当前凭证
   世代，成功才合并内存写能力。刷新同一凭证保留已证实写能力，退出、恢复或接受新凭证撤销。
   迟到结果不能授予另一会话，失败、取消和未知网络结果均不授予且不自动重复写入。
4. 复用现有模块：账号 `domain` 提供可选首次操作接口，`data` 校验响应后完成尝试，
   `presentation` 管理单次提交及成功后读取失败，参考 UI 提供明确确认与错误反馈；
   `app` 只接入部队验证器，保持现有公共方法和构造签名兼容。
5. 账号页三档宽度继续限宽单栏；首次操作确认、配置重建、重复点击、取消和能力撤销需要合成
   设备验证。核心测试覆盖凭证替换、刷新、退出、取消及迟到成功；数据测试覆盖请求一次、
   精确表单、成功负载缺失与错误码。同步独立 Maven 消费、安全负向门禁和三语资源。
6. 本批实现与合成验证不等于真实写入成功。真实签到、领奖及其他互动必须由用户选择具体
   操作后执行；先前消息已读授权不扩展为其他写入授权，不保存账号响应或凭证。

## 证据与范围

2026-09-18 使用本机无头 Chrome、移动视口与移动 User-Agent 访问官方移动站
`https://ff14risingstones.web.sdo.com/mob/index.html#/index`。首次可能收到浏览器挑战，

## 最终目标与执行顺序

1. 完成官网全部功能的原生移植，逐项核对页面、接口、入口和可用行为；有服务实现但没有
   原生交互入口的能力不算完成。真实账号未验证的行为与源码、夹具证据分别记录。
2. 全部功能完成后，从整体 App 导航、信息结构、页面层级和任务路径评估 UI/UE，再直接实施
   专项重构；参考官网视觉与结构，以及百度贴吧等成熟移动应用的交互体验。
3. 最后专项优化路由、转场、加载、返回及形态变化的动画，以 iOS 的连贯流畅体验为目标，
   使用原生 Android 平台能力完成，并验证系统返回、取消手势及无障碍动画偏好。

当前仍处于功能移植阶段；新增功能所需的适配布局不代表整体 UI/UE 和动画专项已完成。

5. 新增可选浏览服务与查询、目录、游标返回类型，保留原有服务、列表枚举和数据类签名。

6. 紧凑宽度列表到详情，中等与展开宽度保留列表和详情；筛选使用可滚动原生面板，按原选择

   回归、独立 Maven 接入及真实 Android 只读验证。功能证据与 UI/UE 专项验收分开。

## 投影台搜索与收藏操作设计

1. 仍复用 `glamour-*`；装备、眼镜、配饰候选来自官方 `gameData`，收藏夹及优惠券来自官方
   投影台服务，不增加模块组。先核对公开脚本中每项操作，完整请求证据不足的操作不猜参数。
2. 候选读取沿用 `searchEquip?page&limit=20&name`、`getGlassesList?name`、
   `getOrnamentList?name`。当前匿名均返回 `10403`，真实形状用已登录 Android 的固定只读组
   核对。装备支持分页，眼镜保留款式分组；选定候选后使用其编号与准确类型标记查询投影。
3. 收藏夹创建、改名、公开设置、删除、指定收藏，以及优惠券领取均是写操作，只由用户明确
   操作触发，不能用于自动能力探测。默认文件夹限制、删除影响及领取是否包含关注均以官网
   行为为准，在原生提交和确认文案中说明；真实验证阶段只读取，不自动执行这些写入。
4. 复用已验证的 `GlamourAuthenticated` 和原登录 UA；不因目录读取授予额外写能力。
   通过可选扩展提供新增收藏管理契约，保留原有公开服务和数据类签名。认证失效清理状态。
5. domain 保存操作与结果契约；data 精确映射请求和响应；presentation 独立管理候选搜索、
   并发取消、文件夹选择、提交和刷新结果；UI 提供候选选择、管理和确认；app 不解析接口。
6. 紧凑宽度使用单列滚动选择面板，中等与展开宽度限制面板最大宽度并保留原列表/详情选择。
   搜索、选项与提交状态在窗口变化中保留，关闭面板取消尚未完成的只读请求。
7. 夹具验证准确请求、分组、分页、错误与空结果区分；状态测试验证迟到结果、认证清理和
   提交成功但后续刷新失败；设备测试验证三档宽度的明确操作、取消和返回，写入使用合成服务。
   同步三语资源、独立 Maven 消费与兼容性记录，源码、设备模拟和真实读取证据分别记录。

### 搜索与收藏交互实现证据

- Android 四个固定只读请求均返回 `10000` 且非空：装备为 `data.rows`，眼镜为款式分组数组，
  配饰为 `data.rows`，本人收藏夹为带 `count` 的行数组。眼镜描述字段为 `des`，同时兼容
  既有 `desc`；图标兼容 `icon` 与 `icon_id`。明确空数组与损坏响应分别处理。
- 原生“按物品查找”先读候选，选中后以编号和正确类型标记查询投稿，保留眼镜款式分组。
  空查询不发请求，装备每页 20 项；取消候选面板不改变已有列表查询。
  新版独立应用沿用 Android 会话，以固定关键词搜索装备，候选非空；选中后对应作品列表非空。
  该检查仅记录布尔结果，没有保存候选名称、编号或作品内容。
- `GlamourCollectionService` 为可选扩展，提供编辑收藏夹与指定收藏。公开脚本
  `app.22e9274d.js` 的 `6b81`、`b775` 及 `chunk-commons.01300528.js` 的 `978c`、`b645`
  确认创建和编辑用 POST，删除用 DELETE，均为表单请求体。名称必填且最多 20 字符；新建默认
  公开；默认收藏夹可改名和切换公开性，但不提供删除。没有证据证明删除会将内容搬到默认夹。
- 收藏选择器始终读取本人的夹，即使来源是作者作品页；选择后明确确认才提交。已收藏使用
  取消接口，不伪造多收藏夹追加或移动。新建成功刷新目录并清空选择，不猜测新夹编号。
- `chunk-78f68c56.3e50ce4c.js` 确认未关注时领取按钮为“关注并领取”；只调用一次
  `glamourFashion/claimCoupon`，不额外调用关注接口。前端 `RequireFollowing` 是已成功并
  关注的展示分支，不应当成失败。原生显示相应提示，已领取不可再次提交。
- 写成功先更新本地状态，再独立刷新；刷新失败提示操作已成功，并仅重试读取。成功修订号
  让 Activity 重建后的当前表单关闭，不依赖旧界面的闭包；迟到的读响应不会覆盖期间确认的收藏。
- 独立详情的作用域在配置重建中保留，在正常退出及会话作用域清理时释放。真实 Activity 重建
  测试覆盖夹选择、新建、收藏、领取与退出；所有写入均使用合成服务，没有操作真实账号。
- 官网响应策略接受 `10000/10002`，投影台按此处理，避免把 `10002` 当失效后重放写请求；
  仍验证读取负载结构。真实请求本次只观察到 `10000`，详见[响应码证据](response-code-evidence.md)。
- 装备和配饰 `-1` 是未装备占位，按官方详情过滤；正编号但缺少名称仍保留为未知装备。

## 论坛互动补齐设计

1. 复用 `forum-*`，只涉及官方帖子详情、评论、点赞、收藏及既有投票；不新增模块。
   论坛正文、评论与投票模型继续位于 domain，原生界面不解析接口响应。
2. `posts/like`、`star`、`comment`、`vote` 使用 POST 表单；`posts/deleteComment` 使用
   DELETE 表单。回复分别传 `parent_id` 和 `root_parent`，图片为单个 URL 的 `comment_pic`。
   官网仅在文本和图片同时为空时拒绝，因此允许仅图片评论；具体投票条件继续以详情分块核对。
3. 图片选择只读本地内容，提交时才通过官方 `getCOSTokenI` 和官方对象存储上传，再提交评论。
   官网评论上传组件使用 `channel=default`；不得继续假定凭证目录一定以 `posts/` 开头，
   仍需严格限制上传主机、相对目录和临时凭证有效期。选图取消不能产生远程写入。
4. 所有互动都改变服务端状态，只由明确操作触发；不使用它们自动探测。保留 `ForumWrite`
   和独立 `ForumImageUpload` 门槛，缺少证据不因登录或账号摘要成功就开放写入口。通过可选
   服务扩展提供图片能力查询，保持旧服务的公开签名。
