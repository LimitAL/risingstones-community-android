# 关注传输的严格成功码与单次发送

依据缓存 Apple 客户端 `GlamourAPIService.performRelationMutation`，关注 POST `api/home/userRelation/follow` 与取消关注 PUT `api/home/userRelation/cancelFollow` 只有业务码 10000 确认成功；本地两个参考提交对应文件一致。10002 不再被这两个方法视为成功，其他幻化读取／写入保留原成功码策略。

离线复现表明旧共用实现会在 HTTP 401／403、业务认证失败／身份冲突之后刷新授权器并再次发送原写请求。本批仅这两个方法不再刷新、等待冲突解决或自动重放；保持现有认证失败异常。业务拒绝保留错误原因，取消继续传播，网络／畸形响应仍按既有异常传播，不伪称发送失败或服务器未写入。共用客户端原有非 GET／HEAD 不换备用主机、底层非读取传输不重试／重定向的保护不改。

请求 UUID、现有临时标识生成与 query／form 布局、取消关注 JSON 及既有认证能力不变，不把 tempsuid 当幂等键。新增私有参数仅两方法启用，其他方法默认保持旧行为。未增加公开接口、凭据、权限、上传、缓存或重试能力。

新独立 `GlamourFollowSingleAttemptTest` 使用严格有限合成传输，只有两种明确方法／端点和两个 `.invalid` 主机可被接收；无 DNS／Socket 或真实账号。覆盖空 data 的严格成功、10002 拒绝、HTTP／业务认证失效、取消、传输故障、缺少能力及不换备用主机。原模块读取刷新／其他业务码与拒绝信息回归保留，不修改旧受保护发布测试。

本批只消除同一次调用内部的认证重放，不代表关系页按钮已接入，也不解决调用方再次点击、持久未知结果、风险确认及新旧尝试恢复。这些需要独立合同与界面接线，不能据此宣称关注流程完整。没有真实关注、取消关注或服务端查询；真实服务、Maven与原生界面未验。
